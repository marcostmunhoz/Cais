# Cais behavior

How Cais behaves and why. Each rule gives its reason when it is not obvious. Agent access has its own document ([agents.md](agents.md)), as do the security model ([security.md](security.md)) and the architecture ([architecture.md](architecture.md)).

## Principles

- **Production does not write by accident.** A production environment opens in Read-only; to write, you have to change the tab's mode, and Auto-commit on production asks for confirmation.
- **Secrets do not leave the main process.** The interface sends the password once, when saving, and never receives it back. No password or token in any log.
- **The interface does not know the engine.** Everything that depends on the database (dialect, keywords, introspection, statement classification) comes from the driver and the dialect. MySQL is the first engine and BigQuery the second (read-only).
- **The app does not change `gcloud`.** It only lists the logged-in accounts and generates tokens: the Cloud SQL login token and the BigQuery access token.
- **Few options.** A safe default is worth more than a setting. The fixed values in this document (row limits, inactivity time, agent levels) are fixed on purpose; a new option only gets in with its reason recorded here. The BigQuery preference **Estimate while typing** (off by default) has its reason recorded in "Estimate while typing" below.

## Screens

- **Main:** sidebar (projects › environments › Scripts and databases › tables and views › columns), tab strip, tab bar, editor on top, results below and status bar. At the bottom of the sidebar are **Credentials**, **Agents** and **Trail**.
- **Tab bar:** `project › environment` (with the production badge when it applies), connection state with Connect, Reconnect or Disconnect, database selector, session mode (**Read-only · Transaction · Auto-commit**; the selector lists only the modes the engine accepts, and an engine that accepts one mode shows a fixed badge in its place, with nothing to choose), Save and Run (which becomes Cancel while running). On an engine that answers a dry run (BigQuery), the **Estimate while typing** switch sits between the dataset selector and Save. With an open transaction, the bar "Transaction open · N statements · time" appears, with **Commit** and **Rollback**.
- **Registry:** projects, environments (with each one's agent access) and credentials.
- **Agents:** the access switch, pending requests, active grants, each environment's level and recent requests.
- **Trail:** everything that ran in Cais, read-only.
- **About:** version, runtime and the new-version check, in a window of its own (see [About](#about)).
- **States:** nothing registered (empty state with the first step), disconnected (also after inactivity), connecting, connected, running, connection error (with the message), transaction open (statements and time) and truncated result.

The interface follows the system's light or dark theme and uses the system fonts. Production shows with a warning stripe and color on the tab and the bar.

## Projects, environments and credentials

- **Project › environments.** An environment has a name, host, port, an optional default database, a credential, a production flag and the agent access level. **Production** comes checked when the name is `pro`, `prod` or `production`, and can be changed.
- **A credential is a registry entry of its own**, used by as many environments as needed, so user and password are not repeated environment by environment. The registry shows how many environments use it. Deleting a credential in use is refused, with the list of environments; deleting a project that still has environments or scripts is also refused.
- **Two credential types:**
  - *User and password.* The password is encrypted by the system vault (`safeStorage`, Keychain on macOS, Secret Service on Linux). Without the vault available, Cais refuses to save the password: it never writes a password in plain text. On Linux the vault only counts with a real keyring (GNOME Keyring, KWallet): if Chromium falls back to storage without a keyring (`basic_text`, which uses a key fixed in the code) or does not know which one it used (`unknown`), Cais treats it as unavailable, and the refusal adds how to install or unlock the keyring and the `--password-store=gnome-libsecret` option. A Google IAM credential does not use the vault and keeps working. In the form, an empty password keeps the current one.
  - *Google IAM via gcloud.* An account chosen among those logged in to `gcloud` (or typed in), optional service account impersonation and a database user derived from the email and editable: a user account becomes the part before the `@`; a service account becomes the email without `.gserviceaccount.com`.
- **Test connection** checks host, port and credential before saving.
- **Project and environment names** are trimmed, normalized to NFC and free of invisible characters, unique ignoring case, and cannot contain `/`, because the `project/environment` address agents use would become ambiguous.
- **Duplicate environment** (environment menu in the tree, or the Duplicate button in the form) opens the new-environment form already filled in, with "(copy)" in the name and the project changeable. Saving is the person's review and signs the new environment (see [Registry protection](#registry-protection)).
- **Duplicate project** (project menu) asks for the name and copies all the environments in a single operation, with the same credential and the same level setting from the registry, without the scripts. It is refused if any environment of the project is blocked: a copy cannot make an environment changed outside Cais trusted. The Trail records "Environment created (copy of project/environment)" for each environment, with the copy's agent access level.
- **Rename project** from the project menu in the tree or the pencil on the group header in the Registry. The Trail records one line per environment. Changing only the case also counts as a rename. The person's connections continue (host, port and credential do not change).
- **Renaming a project, renaming an environment or moving an environment to another project changes the agents' `project/environment` address**, so it counts as an environment change: the 15-minute grants are revoked and pending requests expire. A pending request with the old name would mislead whoever approves.
- **A corrupted file does not prevent opening.** A data file that fails validation is kept aside (`<name>.corrupt-<date>.json`, never deleted) and the app opens empty at that point, with a warning.

## IAM login on Cloud SQL

- Cais uses the documented manual Cloud SQL login: the token from `gcloud sql generate-login-token --account=<account>` (with `--impersonate-service-account` when configured) goes in as the password through the `mysql_clear_password` plugin, with TLS required. There is no proxy or connector running separately: the connection goes straight to the environment's IP and port.
- TLS encrypts without verifying the certificate (`ssl-mode=REQUIRED`), because Cloud SQL uses its own CA.
- **What the instance needs:** the `cloudsql_iam_authentication=on` flag; the account (or service account) registered on the instance as an IAM database user, with the MySQL privileges the work needs; the Cloud SQL Instance User role (`roles/cloudsql.instanceUser`) or equivalent for the account that generates the token (the impersonated one, when there is impersonation); and a network route to the instance's IP and port.
- The token stays in memory for 50 minutes per account and service account, and never goes to a log.
- **Finding `gcloud`:** an app opened from Finder (macOS) or the applications menu (Linux) does not inherit the shell's PATH. Cais looks in the current PATH, then through the login shell (`$SHELL -lc 'command -v gcloud'`, once) and then in `/usr/local/bin/gcloud`, `/opt/homebrew/bin/gcloud`, `~/google-cloud-sdk/bin/gcloud` and `/opt/homebrew/share/google-cloud-sdk/bin/gcloud` (macOS), and `/usr/bin/gcloud`, `/snap/bin/gcloud` and `/usr/lib/google-cloud-sdk/bin/gcloud` (Linux).
- When the account needs to log in again, the error gives the command: `gcloud auth login <account>`.
- The app only runs three commands: `gcloud auth list`, `gcloud sql generate-login-token` and `gcloud auth print-access-token --account=<account>` (with `--impersonate-service-account` when configured; this is the BigQuery token, kept in memory for 50 minutes, separate from the login token). No command that changes `gcloud`.

## BigQuery (read-only)

BigQuery is the second engine, and in this version it only reads: for the person and for agents. What is outside this version, and what each item requires, is in [roadmap.md](roadmap.md). The interface does not change shape: what depends on the engine (dialect, term, capabilities) comes from the dialect and the driver, and the screen says **dataset** where MySQL says database.

### Environment

- **Fields:** Google Cloud project (the id where jobs run and are billed), optional default dataset (this is the "default database") and optional byte limit per query. There is no host or port. There is no location field: BigQuery infers it from the query (the default dataset resolves the region of a query with no table, which would otherwise default to US), and Cais repeats the job's location on later reads (pages, cancel). A query that mixes datasets from different regions is refused by the server ("Not found: Dataset … in location").
- **Credential:** must be "Google IAM via gcloud"; user and password are refused on save. Cais asks `gcloud` for the access token (`gcloud auth print-access-token --account=<account>`, with `--impersonate-service-account` when configured), keeps it in memory for 50 minutes and, if the server answers 401, requests a new one once and retries. What the account needs: `roles/bigquery.jobUser` on the project and `roles/bigquery.dataViewer` on the datasets read; the server's refusal arrives with this hint.
- **Test connection** checks the token, lists the datasets and runs a dry run of a `SELECT 1`, which checks the permission to create jobs in the project.
- **Why the limit field:** BigQuery charges for what it reads, and an unfiltered query on a terabyte-sized table costs a lot before any sign of trouble. That is why the limit is per environment and not a fixed value in the app: a project with TB-sized tables wants a low ceiling, while a project with a slot reservation (capacity paid separately) does not pay per byte read and may not need it. A new environment already comes with 100 GiB (binary units, GiB = 2^30 bytes), a ceiling that blocks the expensive mistake and lets ordinary work through. Empty means no limit: no question and no `maximumBytesBilled`. The field is a whole number of GiB, 1 or more. The limit protects the bytes read, and only those (see [security.md](security.md#bigquery-read-only)).
- Changing the project, the credential or the limit counts as an environment change, like changing host and port in MySQL: agent grants are revoked and pending requests expire, and the registry signature covers the new fields.
- **Older Cais:** a Cais without the BigQuery engine that opens a `catalog.json` with a BigQuery environment sets it aside as corrupted (`.corrupt-<date>.json`, nothing is lost). After registering a BigQuery environment on a machine, there is no going back to an earlier version on it.

### Tab and tree

- **Always Read-only**, in any environment, production or not. In place of the mode selector the bar shows a fixed "Read-only" badge, with a padlock: it takes no click or focus, the color is neutral (so it is not confused with the yellow Production badge), the reason is in the tooltip ("BigQuery is read-only in this version") and the screen reader reads "Session mode: Read-only". The badge comes from the general rule, not from the engine name: any engine with a single mode shows only the badge, and with more than one the selector comes back, listing only the accepted modes. There is no Commit, Rollback or grid editing. The status bar says BigQuery. The main process refuses a mode the engine does not accept regardless.
- **Dataset selector:** switching dataset checks that it exists (`datasets.get`) and makes it the default for the following queries (names without a qualifier). The Trail records the line with the verb `DATASET`. The current dataset lives in the tab's memory: BigQuery keeps no session in this version.
- **Tree:** datasets › tables and views (materialized view and external table get their own mark) › columns with the full type (`STRUCT<…>`, `ARRAY<…>`, `NUMERIC(10, 2)`). A dataset's columns are read when it is opened, by `tables.get` on each table: it costs no bytes (reading `INFORMATION_SCHEMA` would cost, with a minimum per query). While the columns arrive, the dataset row shows "Reading…" on the right; there is no count, because it would need a new main-process channel for a few seconds of waiting. **Refresh schema** reads again.
- **Editor:** GoogleSQL highlighting (backticks, `#` and `--` as comments, double quotes as strings) and autocomplete from the tree, with the same rules as MySQL (see [Editor](#editor)): `dataset.` lists the tables, `dataset.table.` and `alias.` list the columns, and an unqualified column comes from the tables in the `FROM` and `JOIN` of the statement under the cursor. The backtick path (`` `project.dataset.table` ``) works, and the project is ignored. The editor reads on its own the columns of the datasets the statement mentions (`tables.get` on each table, no byte cost, and without opening the dataset in the tree): once per dataset, after a pause in typing, and a read that fails is not repeated until **Refresh schema**. There is no local syntax check on BigQuery (no GoogleSQL grammar is bundled): the syntax error comes from the server, and the editor shows it with Estimate while typing on (see below).
- **Double-clicking a table** runs `` SELECT * FROM `dataset`.`table` LIMIT 100; `` through the normal path. On BigQuery `LIMIT` does not reduce the bytes read, so the estimate and the environment limit apply here too.

### Estimate while typing

A switch on the BigQuery tab bar, **off by default**. It applies to all BigQuery tabs and is kept across app launches (`settings.json`, `estimateAsYouType` field, outside the agent access seal: it gives an agent nothing). With it on, Cais runs the dry run on its own for the statement being written, so the person sees the cost and the errors without running:

- **When:** 800 ms after the last key, and when the cursor moves to another statement. The statement is the one Cmd+Enter would run: the one under the cursor, or the selection when it holds a single statement. When the switch is turned on, or when the tab connects, the statement already in the editor is estimated right away. Nothing is sent with the tab disconnected, with an empty field or with more than one statement in the selection.
- **What shows:** in the status bar, "Will process 12 MiB" (over the environment limit: "Will process 3 GiB, over the limit of 1 GiB: it will ask first"); the previous value is dimmed while the new one arrives. If the server finds an error in the text (syntax, a table or view that does not exist, a dataset the text itself writes that does not exist), the error becomes an underline in the editor, on the word the server points at (the `[line:column]` in the message) or on the whole statement, with the message in a tooltip on hover, and the status bar says "The statement has an error". A failure that is not about the text (network, permission to create jobs, quota, a tab's default project or dataset that does not exist) shows only in the status bar, "Could not estimate", without marking the editor.
- **What the app refuses does not go out:** DML, DDL, scripts and the rest of what "Run" refuses are refused here by the same classifier, in the main process, and the status bar says "Not estimated: reason". If the server reads as something other than `SELECT` a statement the classifier let through, that is also a refusal, not an estimate.
- **Saving calls:** the server's answer about a statement (estimate, refusal or text error) stays in memory for 2 minutes (per environment, dataset and text), so going back to a text already estimated sends nothing; a failure along the way (network, permission, quota) is not kept, and reconnecting, re-reading the schema, editing the environment or turning the switch off and on forget what was kept; a new request from the same tab cancels the one in progress, and the answer for a text that has since changed is discarded.
- **Never executes:** the dry run creates no job and bills no bytes. It also **does not enter the Trail**: it is not a statement (nothing ran, nothing changed) and a line per pause would bury the ones that matter. The estimate shown while writing authorizes nothing: "Run" redoes the dry run and asks above the environment limit, as always.
- **Why it is an option (and starts off):** the statement text goes to Google at every pause, including the half-written draft, with the literals the person pasted (names, ids, emails). "Run" also sends the text, but only when the person decides; estimating while typing sends it without the person deciding each time, and some environments (personal data, contracts) do not want that. There is no way to separate what is sensitive from what is not, so the choice is the person's, once, and holds until they turn it off. A safe default (nothing goes out unless the person asks) is worth more than the comfort of estimating automatically.

### Run

Each statement goes through two layers, and a refusal in either one stops it from running:

1. **The app's classifier** (same dialect in the renderer and the main process) only lets queries through: `SELECT`, `WITH`, pipe syntax starting with `FROM` and a query in parentheses. When in doubt, it refuses.
2. **The dry run** (`jobs.insert` with `dryRun`, the only path that also returns the routines used) returns the type the server read and the bytes it would read. If the server does not read the statement as `SELECT` (or does not say the type), the statement does not run. The driver repeats the dry run inside `execute`, so the second layer also applies to anyone who calls it without going through the `SessionManager`.

- **Confirmation rule:** with a limit, an estimate up to the limit runs, with the limit as the job's `maximumBytesBilled`: BigQuery refuses, without charging, whatever goes past it. An estimate above the limit asks before running any statement; in "Run all" the question lists each statement above the limit with its estimate. Whoever confirms authorizes that estimate: the job runs with the larger of the limit and the confirmed estimate rounded up to the next whole GiB. The confirmation only holds for the statement text it was given for. If the text changes, or the new estimate goes past what was confirmed (the table grew between the question and the execution), Cais asks again. If the environment is edited during the dry run, nothing runs with the old data: the person runs again.
- **With no limit**, Cais does not ask and does not send `maximumBytesBilled`; the estimate shows in the footer anyway.
- **Every job** carries the label `cais: person` (or `cais: agent`), which separates in billing what the person and the agents read, and `jobTimeoutMs` of 30 s only on agent requests.
- **Refused for the person:** DML (`INSERT`, `UPDATE`, `DELETE`, `MERGE`), DDL (including `CREATE TEMP`), scripts (`DECLARE`, `SET`, `BEGIN … END`, `IF`, `LOOP`...), transaction control, `CALL`, `EXECUTE IMMEDIATE`, `EXPORT DATA`, `LOAD DATA`, `GRANT`, `REVOKE`, `ASSERT`, more than one statement at a time, the `#legacySQL` directive (and `#standardSQL`) and `EXTERNAL_QUERY`, which runs a query on another database and whose read-only-transaction behavior has not been verified (see [roadmap.md](roadmap.md#to-verify)). Text with an unterminated string, backtick name or comment is also refused. The reason appears after "Read-only:".
- **Errors** from BigQuery become interface messages with the `reason` as the code and the original text collapsed: access denied (with the role hint), not found, invalid query, byte limit, quota, rate, result too large, service unavailable. With no network, "No response from bigquery.googleapis.com", with a reminder about the VPN and the proxy.

### Result

- The usual grid, without editing. The footer shows rows, time, estimated, processed and billed bytes and whether it came from the cache. BigQuery numbers (`INT64`, `NUMERIC`, `BIGNUMERIC`, `FLOAT64`) are right-aligned. Integers, `NUMERIC` and `BIGNUMERIC` arrive as text (without losing precision); `TIMESTAMP` in UTC with microseconds; `DATE`, `DATETIME`, `TIME`, `INTERVAL`, `RANGE`, `GEOGRAPHY` (WKT) and `JSON` as text; `STRUCT` and `ARRAY` as JSON, which the side panel formats; `BYTES` in hexadecimal, cut at 256 bytes.
- **"Fetch up to 50,000" reads the same job:** Cais keeps the job of the last result and reads more pages from it, without a dry run, without a question and without a new charge. If the result no longer exists (BigQuery keeps it for 24 hours, or the text or the dataset changed afterwards), Cais warns "The result of this query is no longer available" and does not run the query again, because a new job would charge again with no estimate and no question.
- **Cancel** uses `jobs.cancel`; closing the tab cancels the job in progress. A job the server already created and the person cancelled before the response is also cancelled.

### Trail and language

- BigQuery lines carry the job id, the estimated and the billed bytes (a re-read of the same job points at the job, without bytes: it was already billed) and, in the detail, the confirmation of a statement above the environment limit (the estimate and the limit, in the language in effect when the line was written).
- The texts come from the catalogs, in both languages, with the engine's term ("dataset") as the key. What goes to agents stays in English (see [agents.md](agents.md#bigquery)).

## Session modes

A tab is a session, which is a connection. The mode and the transaction belong to the tab.

- **Three positions, not two switches:** Read-only, Transaction and Auto-commit. This way the meaningless combination "read-only + transaction" does not exist.
- **Initial mode:** production opens in Read-only; the others, in Auto-commit.
- **Changing mode with a transaction open is refused**: commit or roll back first.
- **Auto-commit on production asks for confirmation.**
- **The mode survives reconnection.** A tab in Auto-commit of an environment that becomes production goes back to Read-only, with a warning.
- **Typed transaction control is refused in every mode** (`BEGIN`, `START TRANSACTION`, `SET autocommit`, `SET … TRANSACTION`), with guidance to use the tab's mode. `COMMIT AND CHAIN` and `ROLLBACK AND CHAIN` open another transaction and only work in Transaction. `COMMIT RELEASE` and `ROLLBACK RELEASE` end the connection and are refused.
- **"Run all"** (Cmd+Shift+Enter) runs in sequence and stops at the first error. Confirmations are asked before running any of them, and Cancel also works between one statement and the next.
- **A cursor on a blank line runs nothing**, and a comment right above a statement belongs to it.

### Read-only

Two layers: a list of what is allowed in the app, which refuses the rest before it leaves, and the session in `READ ONLY` on the server, reasserted before each statement. On BigQuery the layers are different (see [BigQuery](#bigquery-read-only)).

- **Allowed:** `SELECT` (also through `WITH`, `TABLE` and `VALUES`), `SHOW`, `DESCRIBE`/`DESC`, `HELP`, `USE`, `EXPLAIN` of a read (`EXPLAIN ANALYZE` only of a read, because it executes the statement), `SET @variable = …` and `SET NAMES`/`SET CHARACTER SET` with utf8mb4, on their own.
- **Refused even though it is a read:** `INTO OUTFILE`, `INTO DUMPFILE` and reads with a lock (`FOR UPDATE`, `FOR SHARE`, `LOCK IN SHARE MODE`).
- **`EXPLAIN` of a write** is refused with guidance to use Transaction mode: the server refuses `EXPLAIN UPDATE` in a read-only session, and `EXPLAIN` changes nothing.
- **Executable comments** (`/*! … */`, `/*!NNNNN … */`, `/*M! … */`) are refused: the server may skip or run the content depending on the version, so what the app classified would not be what runs. That is why a mysqldump dump runs in Auto-commit or Transaction.
- **Functions that change server state** outside any transaction (failover and replication wait, group replication, keyring, firewall, audit log, version tokens, locking service, masking dictionaries, `innodb_set_open_files_limit`, `innodb_redo_log_*`, `mysqlx_*`) are refused, as is a function with a non-ASCII name (the server matches functions ignoring accents).
- **When in doubt, refuse.** Refusing too much is acceptable; letting something through is not. The classifier uses the same tokenization as the server (details in [security.md](security.md)).
- **Session in utf8mb4 and `sql_mode` without `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES`**, reasserted before each statement, along with `autocommit`. A transaction opened by any path in a read-only session is rolled back immediately. Leaving Read-only restores the previous `sql_mode`.

### Transaction

- The session runs with `autocommit=0`. The bar shows "Transaction open · N statements · time" from the first statement, including a `SELECT`, because even a read holds a metadata lock and can block a migration.
- **The transaction state comes from the server** (the protocol's open-transaction indicator), not from guessing by statement type. This covers failing DDL, temporary tables, cancellation and rare statements with an implicit commit.
- **A statement with an implicit commit** (DDL, `GRANT`, `LOCK TABLES`, `FLUSH` and the like) with a transaction open asks for confirmation. `CALL`, `EXECUTE` and executable comments count as a possible implicit commit.
- `COMMIT` and `ROLLBACK` typed in the editor work and reset the counter.
- **The transaction does not turn into auto-commit, not even through a procedure:** if a statement turns on `autocommit` (for example inside a `CALL`), Cais puts the session back to 0 immediately and shows that what the statement wrote is already committed.
- **Closing the tab or quitting the app with a transaction open asks** Commit, Rollback or Cancel, with Rollback as the default. On quit, the app only closes after resolving all the tabs.
- **If the connection drops with a transaction open**, the tab shows that the server rolled the transaction back, until the next execution, and the Trail records it.
- In Transaction and in Auto-commit the tab keeps its own `sql_mode`, `SHOW WARNINGS` and `ROW_COUNT()`; Cais does not reassert anything before each statement, so as not to erase diagnostics or undo a `SET sql_mode` from a dump.

### Auto-commit

- Each statement commits on its own. On production, entering Auto-commit asks for confirmation.
- If something changes the session's character set, Cais goes back to utf8mb4 before the next statement: with another character set, the driver would corrupt the text it sends.

## Tabs and connection

- **Each tab shows the connection state:** a dot in the tab strip (gray disconnected, pulsing connecting, green connected, red error, with the message in the tooltip) and a badge on the tab bar. A single function decides the state shown in the strip, the tab bar and the status bar. The state dot takes the place of the environment color in the strip; production stays in the orange stripe at the top of the tab, so green does not mean two things.
- **Opening a tab connects right away** (click on the environment, new tab, script or table), so a network failure shows up before running. A failure on open becomes a connection error with the message. Running during the opening waits for the connection in progress.
- **Tabs restored when the app opens stay disconnected** until the person connects or runs: tabs persist across app launches (text, environment, database and linked script), but reconnecting on its own to several environments, production included, is not what the person asked for by opening the app.
- **Disconnect and Reconnect keep the text, the mode and the database.** With a transaction open or a statement running, Disconnect is disabled, and the main process also refuses: disconnecting would be a silent rollback.
- **Inactivity:** after 30 minutes without activity on the tab (connect, run, commit, rollback, change mode or database), the tab disconnects and shows "Disconnected after inactivity". Never with a transaction open or a statement running. The next Run reconnects. The reason: free connections on small instances without cutting off whoever is working; 30 minutes covers a meeting or a coffee. The value is fixed, and the clock lives in the main process.
- **Editing the environment while the tab connects** discards that connection, which used the old data: the tab stays disconnected with the warning "The environment changed while the tab was connecting", and the next Connect or Run uses the new data (going back to Read-only if it became production). Cais does not reconnect on its own, because the person may be changing the environment precisely because the connection was the wrong one. Closing the tab while it connects closes the connection that arrives later.
- **A click on the environment focuses one of its tabs** (the active one, otherwise the last used in this run of the app, otherwise the last in the strip); with no tab of its own, it opens one. **A double click opens another tab**, only if there was already a tab of that environment before the gesture. **New tab** and Cmd+T always open a new one, with a "project · environment" selector.
- **Double-clicking a table** opens a tab with `` SELECT * FROM `database`.`table` LIMIT 100; `` and runs it.
- The environment menu in the tree has New tab, Edit, Duplicate and Refresh schema.

## Editor

- CodeMirror 6 with the MySQL dialect. Highlighting and keywords come from `lang-sql`; schema names (databases, tables, columns and aliases, from the environment's schema, with the current database as the default) come from a Cais-specific source, which reads the statement under the cursor (what the `;` or the `DELIMITER` in effect separates) and not the whole text.
- **Context-aware autocomplete:**
  - **Unqualified column** of the tables in the statement's `FROM` and `JOIN` (`SELECT * FROM customers WHERE na|`), including when the `FROM` comes after the cursor (`SELECT na| FROM customers`), and of the target of `UPDATE`, `DELETE` and `INSERT INTO` (`UPDATE t SET |`, `INSERT INTO t (|)`). Never of all the tables in the database: with no table in the statement, there is no column to offer.
  - **The same column in two tables** of the statement becomes one option per table, with the table in the detail (`c · int`), and goes in qualified (`c.id`, by alias, or by table name when there is no alias).
  - **After the dot:** the alias (also in `UPDATE t x SET x.`), the name of a table in the statement, a database (`database.` lists the tables) or `database.table.`. Names match ignoring case only when there is a single candidate (`lower_case_table_names` varies from server to server): with `Cards` and `cards` in the same database, only the exact name counts.
  - **Subquery:** the subquery sees its own tables and, with less weight, those of the surrounding query (a correlated subquery uses the outer columns). A derived table (`FROM (SELECT …) d`) and a CTE body do not see the surrounding query, and each arm of a `UNION` is separate. The columns of a derived table and of a CTE do not complete, because there is no schema to read (see the [roadmap](roadmap.md)).
  - **Order:** after `FROM`, `JOIN`, `UPDATE` and `INTO` come the current database's tables and then the databases; after `SELECT`, `WHERE`, `ON`, `BY`, `SET`, `AND` and an operator come the columns, then the aliases and the statement's tables, and last the tables and databases; where only a keyword fits, keywords come first. Keywords mix in by what was typed.
  - A name with a non-word character, or that is a reserved word, goes in backticks (`` `order` ``). The schema is the environment's cache: **Refresh schema** reads again.
- **Syntax error while typing:** after 0.6 s without typing, a statement with an error gets a thin wavy underline where the grammar stopped, and the tooltip says "Possible syntax error:" followed by the parser's message (in English, as the grammar writes it). Only the first error of each statement, because the following ones are the parser recovering. At each pause the statement under the cursor and those on screen are checked (at most 40 statements and 60,000 characters at a time), never the whole document: in a pasted script with thousands of statements, only what the person sees is read, and text already read does not go back to the worker. The statement the person is still typing is not marked while the cursor is at its end and what is missing is the end (`SELECT * FROM t WHERE|`); moving the cursor elsewhere marks it. Nothing goes to the server: the check uses DTStack's MySQL grammar (`dt-sql-parser`, ANTLR4, MIT), which runs in a renderer worker, loaded on the first statement. The server still decides: the underline is a warning and does not prevent running.
  - **What is checked:** queries and row changes (`SELECT`, `WITH`, `INSERT`, `REPLACE`, `UPDATE`, `DELETE`, `TABLE`, `VALUES`, a query in parentheses) and a statement whose first word is not a MySQL verb (`SELEC`). DDL, `SET`, `SHOW`, administration and routines are left to the server, because the third-party grammar covers less than MySQL 8.4.
  - **What is not checked, so valid SQL is never marked:** a statement with an executable comment (`/*! … */`), with `MATCH … AGAINST`, `JSON_TABLE` or `FOR UPDATE NOWAIT`, with a temporal literal (`DATE '2020-01-01'`), ODBC escape (`{fn NOW()}`), the `INTERVAL(…)` function, `(TABLE t)` or `(VALUES …)` in parentheses (the grammar reads them wrong), with a name the grammar takes for a keyword (`type`, `off`, `old`, `resource`… outside a call such as `CAST(`), and with more than 200,000 characters. A statement the worker does not read within 10 s restarts the worker and stays unmarked until it leaves memory. The tests check this list against the grammar's own vocabulary and against a corpus of valid SQL verified on a MySQL 8.4.
  - There is no option to turn autocomplete or the underline on or off: they cost no bytes, send text nowhere and prevent nothing (see "Few options" in the [Principles](#principles)).
- Cmd+Enter runs the statement under the cursor (or the selection), which is lightly highlighted; Cmd+Shift+Enter runs all.
- **Shortcuts by system:** the shortcuts in this document are written as on macOS (Cmd). On Linux and Windows, Ctrl takes the role of Cmd (Ctrl+Enter, Ctrl+Shift+Enter, Ctrl+., Ctrl+T, Ctrl+W, Ctrl+S, Ctrl+Shift+S, Ctrl+O), and the interface shows the shortcut of the system it is running on. Cancel is Ctrl+.; on GNOME with IBus the emoji picker uses Super+. and Super+;, so there is no collision.
- The statement separator understands strings, backticks, comments (`-- `, `#`, `/* */`) and `DELIMITER` lines, which belong to the client and do not go to the server.

## Results

- **One result tab per executed statement**; the latest execution replaces the previous one.
- **Up to 1,000 rows per statement**, with the truncated warning and the "Fetch up to 50,000" button. An explicit `LIMIT` prevails, but collection stops at 50,000 rows. A thousand rows cover most queries without weighing on memory or the network.
- **"Fetch up to 50,000" only exists for a plain read**, because it runs the statement again; a `CALL` is not repeated. The row limit also does not cut a `CALL` in the middle: the extra rows are read and discarded, so the procedure does not stop between a `SELECT` and the writes.
- **Cancel** (Cmd+.) uses `KILL QUERY` through a control connection, with a fresh credential (an IAM token obtained when the connection opened may have expired).
- **Virtualized grid:** header with name and type, numbers right-aligned, NULL in gray italics, long text cut off and a side panel with the cell's full value (JSON formatted). Binary shows in hexadecimal, cut at 256 bytes.
- **Copy:** the copy uses the result's values, with pending edits applied, and long text comes out whole (the grid is what cuts it). NULL comes out as the word `NULL` in Copy value and in the Markdown table, empty in TSV and CSV and `null` in JSON; so, in those two, `NULL` and the text "NULL" cannot be told apart. With **one cell** selected (including the whole column of a one-row result, or the whole row of a one-column result), Cmd+C copies only the value, as the server sent it: no header, no TSV quotes and with the JSON and line breaks as they came. Binary comes out as `0x…`; if the driver cut it at 256 bytes, it comes out cut, with `…`, and the grid warns that the copy is partial (the warning goes away when the selection changes). With **a range** (or no selection, which means the whole result), Cmd+C copies as TSV with a header. The Copy menu (button above the grid, right click on the cell and right click on the row number; in the latter, a selection that is not made of whole rows, such as a column, gives way to the clicked row) has **Copy value** (only with one cell), Copy (TSV, with header), Copy as CSV, Copy as JSON and **Copy as Markdown table**, all over the selection or the whole result.
- **Markdown table:** the first line is the column names; the second, the `---` separator, with `---:` on numeric columns (right-aligned, as in the grid). `\` and `|` are escaped (in that order), line breaks become `<br>` and tabs become a space. NULL comes out as `NULL`, binary as `0x…`. There is always a space before each `|` that separates cells, so a value ending in `\` is not read as `\|`. There is no width alignment or cutting of long values: a cell with a lot of text does not stretch the other rows. The other Markdown characters (`*`, `_`, backtick, `<`) stay as they are, so the raw text remains readable.
- A statement with no rows shows "N rows affected · time". An error shows the handled message and the original detail collapsed. Network errors say "No response from host:port" and remind the person of the VPN, the most common case.
- The affected rows of an `UPDATE` count the rows found by the `WHERE`, not only those that changed (the driver turns on `FOUND_ROWS`).

## Grid editing

- **When editing is possible:** a read result without error, whose columns come from **one base table** (not a view, not an expression, no two sources with the same name) with **all the primary key columns** present. The key values cannot contain NULL, FLOAT/DOUBLE, truncated binary or duplicates, and the key cannot have TIMESTAMP: the text read depends on the session time zone and, after reconnecting, the same text can be another row. Generated columns, truncated binary, geometry and vector are not editable. Outside that, the double click says why, for example which key column is missing.
- **Double click, Enter or F2** opens the cell; Enter confirms and Esc cancels. Leaving the editor without typing anything does not change the cell: NULL stays NULL. The cell menu (right click) has **Set to NULL**, **Undo edit**, **Generate cell UPDATE**, **Delete row** (see below) and **Generate INSERT** (and **Generate INSERT without primary key**, see below). Empty text is empty text; NULL only through the menu. Binary and BIT are typed in hexadecimal.
- The bar "N changes in M rows" (and "N deletions", when there are marked rows, separated by `·`) has **Generate SQL**, **Apply** and **Discard**.
- **Delete row** marks the selected rows for deletion. It is in the cell menu and in the gutter menu (right click on the row number, which uses the rows already selected if they are whole rows and the clicked one is among them and, otherwise, selects the whole row) and on the **Delete** key with the grid focused (**⌫** on macOS, which also accepts Delete; the shortcut text comes from `src/shared/shortcuts.ts` and the key is handled by the same rule, `isDeleteRowsKey`). No modifier. With several rows selected, all are marked; if all are already marked, Delete unmarks. Delete marks the rows the selection covers (Cmd+A, whole rows, one cell or a partial rectangle), **except** when the selection is whole columns (a click on the header, which covers all the rows of some columns): then it marks nothing, because nobody chose rows. The same editing condition applies (base table, whole primary key, without the key exceptions); outside it the entry does not appear and Delete says why. MySQL only (`gridEdit`). The mark is pending like an edit: the row shows struck through, in red, and **does not open for editing** (the grid says the deletion must be undone). Nothing goes to the server until Apply. **Undo delete** (menu) removes the mark. **The deletion wins over the row's edits:** cell edits made before marking stay stored, but generate no `UPDATE`, do not count as changes and come back when the mark is undone; an `UPDATE` and a `DELETE` for the same row are never produced. Copy and Generate INSERT ignore the mark: the marked row comes out like any other, with the values as the grid shows them. **Generate cell UPDATE** is the opposite: marked rows leave the selection (the deletion wins), and the entry disappears when all the selected rows are marked.
- **Generate SQL** puts the pending statements at the end of the editor, selected, **first the `UPDATE`s and then the `DELETE`s**, each group in row order, and clears the marks and edits. The `UPDATE` (one per edited row) and the `DELETE` (`DELETE FROM <database>.<table> WHERE <whole key>`) carry the `WHERE` on the whole key and **carry no `LIMIT`**: it is not safe with statement-based replication and would hide a stale key (the "did not find exactly 1 row" warning depends on the `WHERE` matching the whole key). A key with NULL is refused. Database and table come as the server reported them in the result (on a case-sensitive server, `Users` and `users` are different tables). Text with `\`, a control, invisible or direction character goes as `_utf8mb4 X'…'`, so the statement does not depend on `NO_BACKSLASH_ESCAPES` or hide anything from the reviewer. The literal's type comes from the schema (ENUM, SET and BIT exact). If the editor's last statement does not end with the delimiter, Cais ends it first; if a `DELIMITER` other than `;` is in effect, it puts `DELIMITER ;` before the statements. It runs nothing.
- **Generate cell UPDATE** (cell menu, same editing condition: base table and whole primary key) puts at the end of the editor `UPDATE <table> SET <column> = <current value> WHERE <whole key>;` with the literal of the selected value, for the person to type over (for example replacing `'abc'` with an expression such as `NOW()`). With several cells selected in the same column, one `UPDATE` comes out per row, all the literals selected at once (the editor's multiple selection: what is typed applies to all); the limit is 500 cells at a time, and a selection of more than one column does not offer the entry. The value is what the grid shows, with pending edits applied, and the key is the row's as the server sent it. It runs nothing, does not touch the pending edits and does not depend on the changes bar. It also works in Read-only, because it only fills the editor. Before generating, Cais re-reads the schema, as with Generate SQL. The text follows the same rules as Generate SQL (literals, delimiter). This is the way to put a SQL expression in the value: grid editing only writes literals, and what goes to the editor is SQL like any other, which the person reviews and runs with Cmd+Enter. The editor has a single selection, and only this entry creates several: clicking (not even with Cmd or Ctrl) and dragging never add one, and Cmd+Alt+Arrow (Ctrl+Alt+Arrow outside macOS) does not add a cursor. With several selections, Cmd+Enter runs the whole block only when they have exactly the shape this entry generates (each selection inside a different statement, the statements consecutive, and each statement in the range with one selection); in any other shape it runs only the main selection's statement. The server reclassifies everything.
- **Generate INSERT** (cell menu and gutter menu, right click on the row number) puts at the end of the editor, selected, a single `INSERT INTO <database>.<table> (<columns>) VALUES (…), (…);` with one row of values per row of the selection (the whole row of any selection; up to 1,000 at a time, so the result of thousands of rows is not dumped into the editor). Right click on the gutter uses the rows already selected if they are whole rows and the clicked one is among them and, otherwise, selects the whole row. MySQL only (the `gridEdit` capability; BigQuery does not offer the entry). The result must be the read of **a single base table** (not a view, not a join), as with editing, but it **does not need a primary key**: since the INSERT does not find a row by key, the key does not need to be in the result or be free of NULL, FLOAT, TIMESTAMP or duplicates. The columns are the result's, with the table's names (never the alias); generated columns (VIRTUAL and STORED: the server computes them and refuses a value), expressions, duplicates and columns of a type that cannot be written (geometry, vector) are left out, and a warning lists what was left out. If a column is not in the schema or changed type since it was read, the entry disappears and the schema is re-read once. The values are those the grid shows, with pending edits applied (which stay pending), in the same literals as Generate SQL (`\`, controls and invisibles in `_utf8mb4 X'…'`; binary and BIT in hexadecimal; NULL as `NULL`; JSON, decimals and dates as the server sent them; TIMESTAMP as the text read in the session time zone). Binary the grid cut at 256 bytes does not become an INSERT: Cais refuses and names the column and the row, so as not to insert a value that is not the row's.
- **Generate INSERT without primary key** leaves out the primary key columns, so the server fills them with the auto-increment or the default value. It is only offered when the table has a primary key, the result has all of it and the server marks it as the schema says, and the result includes at least one table column outside the key (without one the INSERT would come out with default values only, and the entry disappears). If the key has no auto-increment or default value, the server refuses the INSERT when it runs, and that refusal is the answer: Cais does not guess. Like Generate cell UPDATE, both only fill the editor: they run nothing, also work in Read-only (running is what the mode decides) and do not re-read the schema, because an INSERT does not risk hitting the wrong row.
- **Apply** runs the UPDATEs and DELETEs through the tab's normal path, so the mode rules:

  | Mode | What happens |
  |---|---|
  | Read-only | Apply is disabled; Generate SQL remains available |
  | Transaction | The transaction opens (or continues) and the Commit and Rollback bar takes over; the success notice reminds the person to commit. It asks nothing: Rollback undoes it |
  | Auto-commit on production | Asks for confirmation listing the statements |
  | Auto-commit outside production | Runs directly, like a typed UPDATE, **except when there are deletions**: then it always asks for confirmation, listing the statements, because each `DELETE` is committed immediately and without Rollback |

- **Cascade and trigger:** the bar and the confirmation warn when the schema Cais has shows that deleting from that table reaches others: cascading foreign keys (`cascadedBy`, with the tables: any `ON DELETE` or `ON UPDATE` rule that cascades, `SET NULL` or `SET DEFAULT` counts, so the warning says deleting *may* reach them, and an `ON UPDATE CASCADE` key with `ON DELETE RESTRICT` also shows up) and triggers (of any event: the warning says that, if any is a delete trigger, what it writes does not enter the row count). If part of that metadata could not be read (`foreignKeysComplete` false, `partial` or triggers invisible to this account), the warning says the absence of a cascade guarantees nothing. The warning does not block: the Auto-commit confirmation with a deletion is already always asked, and in Transaction Rollback undoes it. A `DELETE` stopped by a `RESTRICT` foreign key becomes the server's error and interrupts the sequence.

- **After applying**, the query runs again in the same session to show what the server wrote (trigger, rounding, `ON UPDATE`; deleted rows disappear), and an UPDATE or DELETE that did not find exactly 1 row is flagged (on a `DELETE`, 0 is the row someone else had already deleted). If a statement fails in the middle, the rows that did not run keep their edits and deletion marks; in Auto-commit, the warning says that what ran before the error is already saved. If the re-read query comes from another table (the session's database changed), the previous result stays, with the edits that did not run, and the warning says why.
- **Before Generate SQL, Generate cell UPDATE and Apply, Cais re-reads the environment's schema.** If the primary key changed since the read (a migration with Cais open) or the type of a key column changed, editing is refused and the grid starts showing the reason.
- **Running again, switching result, "Fetch up to 50,000" or closing the tab with pending edits or deletions asks** before discarding them (the count includes the stored edits of marked rows and the deletions). Cmd+Enter and Cmd+W with a typed, not yet confirmed value count that value as a pending edit.
- The main process reclassifies the SQL like any other: the grid's restriction is about use, not the security boundary. The main process only accepts the grid origin mark when all the statements are `UPDATE` or `DELETE` (it refuses `INSERT` and the rest with `grid-not-edit`), but it does not check that the `DELETE` is by the whole key: a `DELETE` without `WHERE` sent with that mark would carry the "Grid edit" label in the Trail. The label is not a boundary, because the mode decides what runs and the SQL is reclassified like any other. The Trail records the `UPDATE` or the `DELETE` with "Grid edit", never the cell's old value or the content of the deleted row (the statement text only has the key values).

## Saved scripts

- **A script belongs to the project and appears inside each of its environments** (`shop › dev › Scripts` and `shop › pro › Scripts` show the same list), from most recently used to oldest. This way the same investigation runs on dev and on production without copy and paste. The script keeps the text, the database and where it last ran.
- **Save:** the Save button on the tab bar or Cmd+S. On an unlinked tab it asks for the name, saves into the environment's project and links the tab to the script; on a linked tab it updates the script (text and current database), and the button is highlighted when there is a change. **Cmd+Shift+S** saves as another script.
- **The linked tab shows the script's name** and a `•` when the text differs from the saved one. Saving from one environment updates the project's script, and the tabs of other environments with the same script start showing `•`.
- **Closing a tab with changes** asks Save, Discard or Cancel, after the transaction question, if there is one. **Quitting the app does not ask**: the tabs' text persists and the `•` comes back on reopening.
- **Clicking the script** opens a tab in that environment, already on the script's database, or focuses the tab that already exists. The script menu has Open, Open in another environment, Rename, Duplicate and Delete; the Scripts group menu has New script.
- **Cmd+O** opens the script picker ("project · name"). It opens in the active tab's environment if it is in the same project; otherwise, in the environment of the last run; otherwise, in the first non-production environment; otherwise, in the first.
- **Script names** are unique per project ignoring case (comparing in NFC), up to 120 characters. Invisible, text-direction and control characters are removed (or become a space), not refused. Duplicate produces "Name (copy)", "Name (copy 2)".
- **Scripts created by an agent** carry the "agent" label until the person saves or renames; the copy of an agent script stays marked.
- If the linked tab's script no longer exists when the app opens, the tab becomes unlinked and keeps the text.

## Language

- **The interface follows the system language, in pt-BR or English.** The first preferred system language that starts with `pt` gives pt-BR, with `en` gives English; neither gives English. There is no option in the app: on macOS, **System Settings › General › Language & Region › Applications** changes the language for Cais alone (the package declares both localizations). On Linux the list comes from the session environment (`LANGUAGE` and `LANG`) and there is no per-app choice; to open Cais in another language, start it with a different `LANGUAGE` or `LANG`.
- The language applies to the whole interface: app menu, dialogs, system notifications, errors and refusals shown to the person, and number and date formats. The interface stays in a single language, the system's, with no Electron menus in another.
- **What goes to agents is always in English** (the `cais llm` output, `guide`, response messages): the codes are the contract, and stable text does not break whoever already reads the output.
- **Not translated:** the server's raw message, the agent's text (reason, client, script name), registered names, SQL keywords and markers such as `⟨U+202E⟩`.
- Trail lines stay in the language they were written in: the HMAC chain does not allow rewriting them.
- The interface text uses no exclamation marks, and trade terms stay as people say them (commit, rollback, schema, query).

## Trail

- **Everything that runs in Cais goes in the Trail**, person and agents, in one place:
  - **the person:** each statement run in a tab (mode, database, verb, rows, affected rows, time and error code), the Read-only refusal, cancellation, Commit and Rollback (by the buttons and on closing the tab), mode changes (Auto-commit on production shows as confirmed), a connection that dropped with a transaction open and the `USE` from the database selector;
  - **agents:** each request (SQL, reason, client, database, who decided, whether the commit was automatic and the counts per statement), policy refusals, `schema` and scripts;
  - **configuration:** each environment's agent access level and production flag, environment created or deleted, agent access turned on or off, 15-minute grants (created, revoked, expired) and what the registry protection detected.
- **BigQuery:** the person's lines carry the job id, the estimated bytes (dry run) and the billed ones when there were any, and, in the detail, the confirmation of a statement above the environment limit (the estimate and the limit, in the language in effect when the line was written). The dry run of "Estimate while typing" is not recorded: nothing ran.
- **Result data is never recorded**, nor is the server's error message, which may quote values ("Duplicate entry 'x'"): only the error code and number.
- **A password typed in SQL becomes `***`** on the person's lines: from the first `IDENTIFIED` or `PASSWORD`, everything between the first and the last quote. The mask is deliberately coarse, so that no escape rule, comment or second literal lets a piece escape. Agent lines are not masked: an agent does not run those statements, and masking would let the agent hide text from the Trail.
- **One file per day (UTC)** in `trail/`, in the data folder, with 0600 permission, for **90 days**. A line is at most 128 KB (the stored SQL goes up to 100,000 characters, with the original size noted), and agent lines for a day stop at 64 MB in total, so an agent cannot make the day's file too large to read.
- **A person's statement that is not a plain read, Commit and Rollback get a line before they go out** (with the same id as the final line), so a hang in the middle leaves a trace. A Trail failure never brings down the person's execution, and the screen shows when it stopped writing.
- **Without the Trail, no agent runs on its own.** Each agent request writes one line before running and another at the end. If the line cannot be written (or the day went past the agents' ceiling), what would run on its own becomes an approval request, and even an approval does not run: the request stays pending, with a warning.
- **Each line is chained**: it carries an HMAC of the line with the previous line's code from the same day, with the registry protection key. A line that is altered, inserted, deleted in the middle or without a code, or a day that cannot be read, shows as "does not check out". Deleting a whole day's file or cutting the end of a file does not show (see [security.md](security.md)). Without the system vault there is no key: the Trail writes without chaining and the screen warns that there is no verification.
- **The Trail screen** (sidebar) is read-only and filters by period (last 24 hours, 7, 30 or 90 days), by who (you and agents, only you, only agents, only Cais), by environment and by text in the SQL, the reason or the client. Each day of the period is checked. The Trail does not reopen a query in a tab: it records what ran, it is not an editing history.

## About

- **Where:** on macOS, **Cais › About Cais**; on Linux, **Help › About Cais**. It is a window of Cais itself, the same on both systems and in the app's language, in place of the system's native panel (which has no link or room for the version check). Esc or **Close** closes it.
- **What it shows:** the logo, the app version, the Electron, Chromium and Node versions, the system (`linux x64`, for example), the license (MIT) and the repository address (`github.com/marcostmunhoz/Cais`), which opens in the system browser. **Copy info** puts version, runtime and system on the clipboard, to paste in a bug report.
- **The version check only happens when the person clicks Check.** Opening the window queries nothing, and the app never checks at startup or in the background. The click makes a single `GET` to the GitHub releases API (`api.github.com`), with no token, no cookie and a 5-second limit. What goes out is the machine's IP and the Cais version (in the `User-Agent`), nothing else. The result is kept for 1 hour (the API without a token accepts 60 requests per hour per IP, and a repeated click does not need a new answer); a failure is kept for 30 seconds.
- **The results:** "You are on the latest version"; "A new version is available: X.Y.Z" with the link to that release's page (notes and files), which the app builds from the tag, never from an address in the response; or "Could not check" with the link to the releases page. A network failure, API limit, a repository with no release or a private one (the API answers 404 without authentication), invalid response or timeout all give the same message, with no technical text. Only a tag in the `vX.Y.Z` format counts.
- **The app only opens fixed addresses in the browser:** the repository, the releases list and the page of the release found by the check. The interface chooses the page; the main process builds the address.
- **No notice outside the window:** no badge, notification or toast when there is a new version. The person only sees the result if they ask.
- **No option:** since the check never runs on its own, there is nothing to turn on or off (see [Few options](#principles)). A check at startup would need a switch for whoever does not want to talk to GitHub, and so it does not exist.
- **No automatic update:** Cais does not download or install anything (see [What Cais does not do](#what-cais-does-not-do)).

## Registry protection

A process that writes to the data folder could point an environment's host at another server (Cais would send the credential there; with `caching_sha2_password`, the server receives the password) or remove an environment's production flag. The registry protection makes those edits visible.

- **What is signed:** each environment, with the project name, the credential it uses and that credential's encrypted password, and the agent access switch. The signature uses a key kept in `seal.json`, encrypted by the system vault.
- **An environment that does not match when the app opens** (edited, added, pointed at another host, with the credential swapped or the project renamed outside Cais) opens **blocked**: nothing connects to it, neither the person nor agents. It also opens marked as production and with agent access "Everything needs approval", with a warning and a line in the Trail. The registry shows the reason; saving the environment after checking host, port, credential, production and agent access unblocks it. A blocked environment is never re-signed on its own.
- **Without `seal.json`** (file deleted or a key the vault cannot open), all registered environments are blocked and marked as production in the same way: deleting the file does not make anything trusted. Those awaiting review sit on a signed list, so restarting before reviewing them all does not raise a false alarm; each time the app opens, a pending environment goes back to production with "Everything needs approval".
- **"Test connection" with a blocked environment's credential is refused**, because the draft's host may be the edited one.
- **Agent access turned on without a signature opens off.**
- **Without the system vault**, nothing is signed: all environments stay on "Everything needs approval" for as long as that lasts (in memory only, without writing to the file), the field is locked in the registry, and edits made without the vault ask for review when it comes back.
- If Cais crashes between writing `catalog.json` and `seal.json`, the environment opens blocked and saving it again is enough. This is the safe side.

## What Cais does not do

| What | Why |
|---|---|
| Hosted web app | The browser does not speak the MySQL protocol and cannot reach the local `gcloud`. |
| Other databases (PostgreSQL etc.) | The driver and dialect contract is agnostic; a new driver comes in when there is use for it. |
| Writing to BigQuery (DML, DDL, scripts, transaction, grid editing, agent writes) | It requires one BigQuery session per tab, classification of a whole script and the cost of the write under the same byte limit. The order and what each item requires are in [roadmap.md](roadmap.md#bigquery-after-the-read-only-version). |
| History to reopen queries, scripts as `.sql` files in a folder, folders inside Scripts, exporting a result to a file | Saved scripts live in the app's registry, and the Trail records what ran. Copying as TSV, CSV, JSON or a Markdown table covers data output. |
| MCP server | The CLI covers agents with a shell. An MCP adapter would be a thin layer over the same local protocol. |
| DDL and statements with an implicit commit by agents | They cannot be undone. An agent only reads or does DML inside a transaction. |
| SSH tunnel, Cloud SQL Connector, syncing between machines | Direct IAM login, with TLS, covers Cloud SQL without a proxy. |
| TLS on user-and-password credentials, verification of the server certificate | A user-and-password connection goes without TLS, intended for servers reached over a private network or VPN; IAM requires TLS, but Cloud SQL uses its own CA, which Cais does not check (see [security.md](security.md#known-limits)). |
| Automatic update, an automatic version check or a new-version notice outside the About window | Without a Developer ID on macOS the system would not let the app replace itself, and the Linux `.deb` is installed by hand. An automatic query would send the IP and the version to GitHub without the person asking, and would require an option to turn it off. The About window only queries when the person clicks. |
| Developer signing and notarization of the app | The package gets a local ad-hoc signature (see the README). |
| Options for language, inactivity time, row limits | They follow the system or are fixed (see [Principles](#principles)). |
